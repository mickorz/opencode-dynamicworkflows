Dynamic workflow orchestration for OpenCode.

Build complex AI workflows using agents, parallel execution, control flow, verification, checkpoints, and reusable workflows.

![OpenCode Dynamic Workflows intro](assets/intro.png)

## Features

- 🤖 Multi-Agent Workflows
- ⚡ Parallel Execution
- 🔀 Dynamic Control Flow
- ✅ Verification
- 👤 Human-in-the-Loop Checkpoints
- 🧩 Child / Nested Workflows
- 🔌 OpenCode Integration

> In one sentence: the Main Agent generates a JavaScript orchestration script, which the runtime executes in a VM sandbox. Tasks are dispatched via `agent() / parallel() / sequence() / fallback() / race()` to many independent sub-sessions running in parallel; the script aggregates the results and returns only the final summary to the main context — solving the context-pollution problem of large parallel batches. Built on the OpenCode v1 plugin API.

## Understand It in 30 Seconds

**The problem**: when you ask AI to analyze 20 files in parallel, the process and output of all 20 sub-tasks flood your main conversation context — the window overflows and follow-up turns slow to a crawl.

**The solution**: you describe the goal in natural language → the Main Agent generates an orchestration script → the plugin executes it in a sandbox, dispatching tasks to dozens of independent sub-sessions → the main conversation receives only one aggregated result plus per-task timing and token stats. While running, the TUI sidebar shows a live progress tree:

![TUI live workflow tree](assets/tui_workflowtree.png)

Click any node in the tree to open the **node detail view**: see that agent's final result directly (text or pretty-printed JSON — structured output is no longer a blank wall), along with execution metadata (model, duration, tokens, sub-session) and an Open Session entry to replay the full process.

**Nested workflows**: sub-agents with `agentType: 'general'` can themselves invoke the `workflow` tool, chaining multi-level workflows into one big flow (e.g. root workflow → parallel fan-out at the middle layer → multiple leaf workflows). Each nested run gets its own token and duration accounting, rendered in the TUI sidebar as a **hierarchy tree** — nested subtrees hang directly under the triggering node, indented level by level:

![TUI nested workflow hierarchy tree](assets/workflow-tree-tui.png)

**You don't need to write code.** Orchestration scripts are generated by the Main Agent via a built-in skill; when you want to go deeper, see the [workflow-authoring DSL reference](https://github.com/mickorz/opencode-dynamicworkflows/blob/main/skills/workflow-authoring/references/runtime.md).

## Prerequisites

1. **OpenCode v1 installed** with a working provider/model (normal conversation works). See the [OpenCode docs](https://opencode.ai/docs/) if not.
2. **Node.js 18+ and npm**: only needed to run the installer (npx) and npm operations; the plugin itself is loaded by OpenCode's built-in runtime and does not depend on your local Node.
3. Windows users: run npx commands in **PowerShell or cmd** (npm's bin forwarding has issues under git-bash).

## Installation

One command (run in any directory; interactively merges config and installs skills, with an automatic `.bak` backup of the original config):

```powershell
npx @mickorz/opencode-dynamic-workflows install
```

**Restart OpenCode** after installation. See [docs/configuration.md](docs/configuration.md) for the three installation modes (global / current project / pinned version).

Companion commands:

```powershell
npx @mickorz/opencode-dynamic-workflows update      # upgrade to latest
npx @mickorz/opencode-dynamic-workflows uninstall   # interactive uninstall
npx @mickorz/opencode-dynamic-workflows doctor      # environment check (read-only)
```

## Quick Start in 5 Minutes

**Step 1: verify the installation.** After restarting OpenCode, ask the Main Agent:

```
What tools do you have?
```

The tool list should include `workflow` (asking "what skills do you have" should show `workflow-authoring`). You can also run `npx @mickorz/opencode-dynamic-workflows doctor` for an environment checklist.

**Step 2: run your first workflow.** Say this to the Main Agent (paste as-is):

```
Execute the following script with the workflow tool, exactly as-is:

export const meta = { name: 'smoke_test', description: 'minimal smoke: 3 agents' }

phase('Scan')
const info = await agent('List the files in your current directory, output only the first 10 lines')

phase('Echo')
const results = await parallel([
  () => agent('Explain workflow orchestration in one sentence'),
  () => agent('Explain deterministic replay in one sentence'),
])
return { info, results }
```

**Step 3: read the result.** The tool returns something like this (values vary by model):

```
Workflow smoke_test completed: 3 agents, 11.6s, 612 tokens total (runId: run-xxxxxxx)
Phases: Scan > Echo

Agent summary:
  [ok] <task name> (Scan) 120 tok ($0.0012)
  [ok] <task name> (Echo) 96 tok ($0.0009)
  [ok] <task name> (Echo) 88 tok ($0.0008)

## Result
{ "info": "...", "results": ["...", "..."] }
```

All three agents `[ok]` with full JSON under `## Result` means it works. You can also just speak naturally and let the Main Agent generate the script itself, for example:

```
Use workflow to analyze all markdown files under the docs directory in parallel, then summarize into a bullet-point list
```

**Go further: model selection and structured output.** Sub-tasks can specify a model (use one available in your config) and constrain the return format with a schema:

```
Execute the following script with the workflow tool, exactly as-is:

export const meta = { name: 'model_schema_demo', description: 'model selection + schema-constrained return' }

const SCHEMA = { type: 'object', properties: { ok: { type: 'boolean' }, summary: { type: 'string' } }, required: ['ok', 'summary'] }
const r = await agent('Read package.json in the current directory and summarize its purpose in one sentence', { model: 'openai/gpt-4o-mini', schema: SCHEMA })
return r
```

`r` is directly a JSON object (`r.ok`, `r.summary` accessible without parsing). See the "Model Orchestration" and "Schema Structured Returns" chapters of [how-to-guides](docs/how-to-guides.md).

**One more step: timeouts and retries.** Set a per-task timeout for slow jobs; recoverable failures (including timeouts) retry automatically:

```
Execute the following script with the workflow tool, exactly as-is:

export const meta = { name: 'timeout_retry_demo', description: 'single agent timeout and retry' }

// 60s hard timeout, up to 2 automatic retries on recoverable failure (3 attempts total)
const r = await agent('Analyze the docs directory and output a bullet-point summary', { label: 'docs-analysis', timeoutMs: 60000, retries: 2 })
return r
```

Key points: `timeoutMs` in milliseconds, omitted means no hard timeout; `retries` capped at 3, timeouts count as retryable; you can also set run-wide defaults via tool args `agentTimeoutMs` / `agentRetries` — per-agent `timeoutMs` / `retries` win. See the "Timeouts & Retries" chapter of [how-to-guides](docs/how-to-guides.md).

**Re-run the same script with parameters: args.** Scripts read the global `args`; append parameters to your instruction without touching the script:

```
Execute scripts/node-detail-ab-test.js with the workflow tool, exactly as-is,
args = {"model": "biangfeng-gateway/glm-5.2"}
```

On the script side (with defaults, parameter optional): `const modelOptions = {}; if (args && typeof args.model === 'string') modelOptions.model = args.model`, then spread `...modelOptions` into `agent()` options. The sandbox disables `Date.now()` / `Math.random()` — external values (lists, paths, timestamps) are injected via `args`. See the "Parameterized Runs" chapter of [how-to-guides](docs/how-to-guides.md).

## Core Concepts

- **Sub-session isolation**: every agent runs in an independent sub-session; use subagent navigation inside the parent session to inspect each full process — the main conversation only gets the summary.
- **Read-only by default**: `agent()` uses the read-only explore sub-agent by default; tasks that write files must explicitly pass `agentType: 'general'`.
- **Nested workflows**: general sub-agents can call the `workflow` tool again to chain multi-level flows; the TUI sidebar shows the hierarchy tree (nested subtrees under the triggering node). See the "Nested Workflows" chapter of [how-to-guides](docs/how-to-guides.md).
- **Background & resume**: tool arg `background: true` returns a runId immediately without blocking; after an interruption, `resumeFromRunId` resumes from the breakpoint — completed agents are replayed from the journal without re-spending tokens.
- **Quality helpers**: `verify` (adversarial verification) / `judgePanel` (judge panel picks the best) / `retry` (bounded retry) / `checkpoint` (human confirmation gate; rejection is a hard stop).
- **Composite control flow**: `sequence` / `fallback` / `race` / `check` composite nodes plus `parallel` form one unified control model; the TUI sidebar groups by composite level.

## Feature List

- `workflow` custom tool + `workflow_control` control tool (status / stop)
- Scheduled tasks: create with natural language like `/schedule run xxx.js hourly`; deterministic execution at the scheduled time (no LLM in the loop); multiple OpenCode instances on the same project never double-fire; execution history queryable
- VM sandbox determinism guardrails (no `Date.now()` / `Math.random()` / import / require — deterministic replay)
- DSL: `agent / parallel / pipeline / phase / log / args` + quality helpers + composite control flow `sequence / fallback / race / check` (+ deterministic helpers `fileExists / commandSuccess`)
- Native structured output (`schema` via OpenCode `format: json_schema`), concurrency control (default CPU cores-2, cap 16), timeout/retry/abort cascading, git worktree isolation, journal-based resume, background runs
- Native child workflows `workflow()`: compose sub-flows directly inside scripts (`await workflow('./sub.js', args)` or by registry name `workflow('daily-review')`), no LLM forwarding; one run shares concurrency quota/abort/journal; parents can be pure orchestration; multiple instances of the same script distinguished by label
- Sub-flow observability: results carry per-sub-flow wall-clock duration and token stats (use wall-clock for config comparisons); TUI groups subtrees per sub-flow
- Workflow Registry: scripts under `.opencode-workflows/workflows/` referenced globally by `meta.id ?? meta.name`, the same identity system as Schedule workflowIds (one script can be both scheduled and composed)
- Nested workflows (legacy): re-invoking the `workflow` tool inside general sub-agents, each level with independent run/journal/token accounting

### Composite Control Flow

One unified four-quadrant model — every composite node takes an array of functions, and nodes can nest any other node:

|        | Execute all                                       | Select one                                  |
| ------ | ------------------------------------------------- | ------------------------------------------- |
| Serial | `sequence` (prev-chain passing, returns last value) | `fallback` (try in order, first success wins) |
| Parallel | `parallel` (order-preserving, failed slots null) | `race` (first success wins, cancels the rest) |

```javascript
// Multi-level degradation: fast model, then strong model; structural errors
// (typo'd script paths etc.) propagate up and are never swallowed
const result = await fallback([
  () => workflow('./fast.js'),
  () => workflow('./strong.js'),
])
if (!result) return 'all fallback paths failed'

// Four-layer verification chain: AI execute -> deterministic check -> AI review -> human gate
await sequence([
  () => agent('Modify src/login.ts', { agentType: 'general' }),
  () => check(() => commandSuccess('npm run build'), 'build must pass'),
  (prev) => verify(prev, { reviewers: 2 }),
  () => checkpoint('Verification passed. Publish?'),
  () => workflow('./publish.js'),
])
```

Semantic rules (details in the workflow-authoring skill):

- **Execution status is not business result**: a node returning any value (including `null` / `{ok:false}`) is an execution success — write your own if for business vetoes
- **Recoverable failure returns null**: same shape as a recoverable `agent()` failure, `if (!r)` just works; structural errors (typo'd scripts / depth exceeded / non-function arrays) propagate directly
- **Human Reject is a hard stop**: a rejected `checkpoint` throws `CHECKPOINT_REJECTED` — fallback will not switch candidates, parallel will not collapse it to null; on resume the rejection deterministically replays (edit the prompt text to re-ask)
- **race cancels locally**: after a winner, other candidates (including agents inside their child workflows) are aborted without touching the root
- **Journal transparency**: composite nodes occupy no callIndex — resume behaves identically to plain await chains
- **TUI composite tree**: the sidebar shows `[Sequence]` / `[Race]` group rows and checkpoint states (waiting for human / approved / rejected), telling "waiting on a human" apart from "hung"

### Scheduled Tasks: Product Boundaries (Design, Not Bugs)

- **OpenCode must be running**: tasks don't execute while the TUI is closed; they resume automatically when reopened.
- **Missed = skipped**: time slots missed during sleep/shutdown are not backfilled; the next future slot fires normally.
- **Multi-instance safe**: multiple OpenCode instances on the same project fire at most once per slot (atomic claim coordination).
- Semantics are at-most-once per slot; workflows that require a human checkpoint are unsuitable for scheduling (they fail outright).

See the scheduled-tasks chapter of [docs/how-to-guides.md](docs/how-to-guides.md).
