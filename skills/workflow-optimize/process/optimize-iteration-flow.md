# 优化迭代闭环流程

一次完整迭代 = 初始化档案 → 备份 → 设计改动 → 执行快照 → 多维评审 → 写报告 → 参悟回填。七步顺序执行，不得跳步。

## 第 0 步：初始化优化档案

1. 按 `reference/ledger-schema.md` 确认三个档案文档是否已存在（与演进报告同目录，路径推导规则见 SKILL.md）：优化台账、指标对比、遗留问题清单
2. 缺哪个建哪个（含表头与本 workflow 的内容指标选型注记）；已存在则只做列完整性检查，缺列补表头，不动已有数据
3. 首次迭代还需把已执行过的历史版本补录进台账与指标对比（数据从历史演进报告与产物快照复算回填，注明"回溯补录"）

## 第 1 步：备份与建档

1. 确认当前最大版本号 N（看脚本目录里 `<name>.v*` 备份与 docs 里的演进报告）
2. 备份当前工作版：`<name>.js` 复制为 `<name>.v<N>-<标记>-<YYYYMMDD>.js`
   - 标记 = 本版主题的短代号（2-3 字母，如 ABC、FH）
   - 首个原始版约定为 `<name>.v1.js.bak`（沿袭历史命名）
3. 工作版保持原名 `<name>.js` 不变，评审与引用始终以它为当前版
4. 优化台账追加当版行：版本、日期、主题标记、备份文件（后续步骤陆续补列，见 ledger-schema 写入时机矩阵）

## 第 2 步：设计改动（一版一主题）

1. 读上版演进报告的"遗留问题清单"，与本版优化目标合并排序
2. 查 `reference/optimize-playbook.md` 的修复手法清单，能复用的直接复用
3. 产出改动清单表（本版只做一个主题）：

| # | 改动 | 位置 | 修复的问题 | 预期验证方式 |
|---|------|------|-----------|-------------|

4. 预期验证方式必须可复算（如"AUTO 残留数 = 0"、"报告含机械小节"），禁止"整体感觉更好"类验收

## 第 3 步：执行与快照

1. 在 workflow 的运行目录执行新版脚本。运行目录从脚本内相对路径（如 `.xflow/...`、`.opencode/skills/...`）推导，推导不出时问用户，禁止假设为当前目录。串行执行多版对比时尤其注意：workflow 的 prepare 脚本会清空重建目标目录
2. 执行完成立即收产物：复制完整产物到 `<产物根>/quality-compare/v<N+1>/`，未快照前不得启动下一版
3. 记录元指标（从 run 结果与 journal 取，不手填）：

| 版本 | runId | 耗时 | token | 轮次 | 流程结果 | 自评（RED/O/Y 或等价） |
|------|-------|------|-------|------|---------|------|

4. 执行失败先走 resume 续跑（journal 回放），失败原因本身也是评审证据
5. 数据落档（数值来自 run 结果与 journal，不手填）：台账当版行补 runId/耗时/token/轮次/结果/自评；指标对比表补本版执行元指标列

## 第 4 步：多维评审（并行 fan-out）

用 workflow 工具发 N 个（建议 4-5 个）并行评审 agent，对比 `quality-compare/` 下所有版本产物。

### 编排职责（主 agent 所有）

- 确定维度集合、分发任务、汇总排名、写报告
- 单个评审 agent 失败返回 null 时：该维度标"未评审"，不重试阻塞、不影响其他维度

### Worker 任务模板（每维度一个 agent，独立上下文）

```text
你是 workflow 产物评审 agent，只负责「<维度名>」维度。

【输入】
- 各版产物目录：quality-compare/{v1..vN}/（每版含 spec_*.md 与校验报告）
- 上版演进报告（遗留问题清单）：docs/<报告路径>

【执行】
1. 逐版读产物中与本维度相关的文件。
2. 只评「<维度名>」：<该维度的检查点描述>
3. 可程序化核验的项（编号连续性、残留计数、行数对账）必须自己复算，
   不轻信产物内报告的自述。
4. 对本维度给出版本排名（第 1 到第 N），每个名次附 1-2 条文件级证据（文件:行）。

【输出格式】
第一行：DIMENSION=<维度名> BEST=v<N>
之后：每版一行 | 版本 | 名次 | 关键证据 |
最后一段：本维度最严重的 1 个问题（若无写"无"）。

【禁止】
- 不改任何产物文件；不评其他维度；不写总体结论。
```

### 维度设计要求

- 机制维度与内容维度必须分开（归因解耦的关键）：
  - 机制类示例：编号落地率、闸门闭环（机审人审一致性）、元信息回填、锚点纪律
  - 内容类示例：覆盖完整性、结构规范性、术语对照、粒度
- 维度间检查点不得重叠
- 上版遗留问题中未被本版修复的项，纳入对应维度持续追踪

## 第 5 步：汇总写报告

先落档再写报告：把评审复算出的机制指标与内容指标补进指标对比表的本版列（口径按 ledger-schema，禁止自创口径），然后主 agent 汇总各维排名为奖牌表，按以下骨架写入 docs（与历史报告同目录）：

1. 执行元数据表（第 3 步的表 + 本版）
2. 评审总排名表（维度 x 名次，综合行给奖牌数）
3. 本版修复验证：每项改动给"生效/未生效/部分生效"结论 + 复算证据
4. 根因分析：问题必须证据链闭合（diff 逐行核对 + journal/产物证据），可附 mermaid 根因链
5. 遗留问题清单（带严重度）：诚实记录，含"报告未捕获但评审发现"项
6. 元结论：区分"机制修复（可归因）"与"内容波动（随机）"
7. 下一步建议（优先级排序）
8. 引用说明：脚本备份路径、产物目录、runId、关联报告

报告规范：无占位符残留；数字全部复算过；引用的文件路径真实存在。

报告定稿后同步落档：台账当版行补奖牌/报告路径/遗留数；本版新发现问题按 schema 追加进遗留问题清单（含验证方式）。

## 第 6 步：参悟回填

1. diff 旧版备份与新版工作版，逐行确认改动与第 2 步清单一致（防止改了没记录的）
2. 把本版新发现写回 `reference/optimize-playbook.md`：
   - 新验证有效的修复手法 → 追加到修复手法清单（带案例出处）
   - 新踩坑（尤其"责任反转"类：模型行为正常但机制坑了产物）→ 追加到踩坑库
   - 评审中暴露的维度盲区 → 追加到维度模板
3. 核对遗留问题清单：逐条比对"报告声称已修"与产物实证，仅实证通过才把状态改已修并填修复版本；连续两版未修的标注跨版失忆风险
4. 回填后 playbook 中每条经验都必须有真实案例出处（版本号 + 报告路径），无出处的删掉
