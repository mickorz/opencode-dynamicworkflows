# 优化 playbook：已验证的修复手法与踩坑库

来源：spec-clarify workflow 四版演进（v1 原始版 → v2 四维校验 → v3 返回约束 → v4 双闸门）的实战验证。
每条经验必须带案例出处；新经验回填时同样要求出处，无出处删除。

## 一、修复手法清单（按验证强度排序）

### 1. 数据质量责任放回数据产生处（根因修复，最强）

指令让产生数据的 agent 直接产出最终形态，而不是先写占位再靠收尾脚本补救。

- 案例：extract 编号从"优先写 UI-XX-AUTO 占位 + normalize 重编号"改为"直接写 UI-XX-001 连续编号，禁止 AUTO"，normalize agent 整体删除，编号落地率 5% → 100%（v3 → v4，报告：v4 产物质量验证 3.1 节）
- 适用信号：收尾脚本对某格式识别不稳、占位符经常残留

### 2. 双闸门判定：机审与人审都过才放行

机械检查结论必须解析并纳入通过判定，不能只信 review 的 RED=。

- 案例：v3 mechanical 判"失败(7)"而报告写"通过"（精神分裂）；v4 加 parse-mechanical + `redCount === 0 && mechFindings === 0` 双闸门，结构性根治（v4 验证 3.2 节）
- 适用信号：两个检查源结论可能不一致的任何流程

### 3. 判定回读文件，不信任 agent 返回文本

需要消费的结论（RED=、findings=N）由专门 agent 从落盘文件读回，与返回文本解耦。

- 案例：v2 的 parse-review、v4 的 parse-mechanical，均比 v1 从返回文本正则解析可靠（三版对比报告第 4 节）

### 4. 写文件的 agent 一律加返回约束

【返回约束】小节限定最终回复为一行完工语或严格格式，禁止复述文件内容。

- 案例：v3 全面加返回约束后耗时 1140.6s（v2 为 2399.9s），token 从 523K 降到 339K（耗时分析报告）
- 覆盖检查：加完要复查是否漏了哨兵类 agent（v4 的 check-source 漏加，单次返回 19,829 tok，v4 验证第 4 节）

### 5. 哨兵 agent 二次确认

只回 EXISTS/MISSING 的哨兵检查，空返回或异常返回时追加一次带读取确认的重查，防偶发空输出误判。

- 案例：v2 首跑 check-source 返回空字符串被误判 MISSING，被迫 resume（三版对比第 8 节）；v4 步骤 4.5 加二次确认

### 6. review 维度专项加固：把历史盲区写成显式检查点

历史版本漏抓的问题（编号残留、表头与数据行列数不一致）追加到对应维度的 checks 描述里，记红色。

- 案例：v4 completeness 维度追加编号落地核查 + 表格结构核查，新抓出"基础番型 11 种 vs 12 种"跨文件冲突（v4 验证 3.2 节）

### 7. 报告元信息由编排层注入实际值

模板占位符（{module}、{profile}）由 workflow 计算好后注入 summary agent 指令，并明文禁止保留占位。

- 案例：v2 残留 {module} 占位且漏列 3 个被校验文件；v4 回填成功 9 文件全列（v4 验证 3.3 节）

## 二、踩坑库

### 坑 1：模型越守约，产物越差——责任反转

指令要求写占位等收尾脚本处理，而收尾脚本对实际格式（反引号包裹的编号列）识别失效时，守约的模型产出裸奔占位，违约的模型反而自洽。三版中 normalize 全部报错，v1/v2 是"违约救了产物"。

- 教训：上下游交接格式没有程序化验证过，等于没设计。改法见手法 1（三版对比 3.2 节）

### 坑 2：校验体系度量的是"校验流程自身一致性"，不是"产物可交付性"

v3 流程 1 轮通过但产物垫底不可交付；v2 三轮不放行但产物第一梯队（RED=1 是真实原文矛盾，诚实上报反被流程判负）。

- 教训：通过判定与产物质量系统性解耦时，先修判定链路再谈产物；真实矛盾不该被流程惩罚性放行（三版对比第 6 节）

### 坑 3：机制修复与内容波动解耦

同一 prompt 下 extract 的内容取舍每版不同（卡二条条件 v2 最全 v4 丢失、术语对照 v3 最全 v4 缩水）。这不是机制退化，是 extract 环节没有内容完整性闸门。

- 教训：评审必须把机制维度与内容维度分开打分，否则内容随机波动会污染机制改动的归因；内容治理需建 checklist 机械检查（v4 验证第 5 节）

### 坑 4：缺跨版记忆，报告指出的问题下版不继承

v3 报告指出过 flow 结束判定丢第三分支，v4 未继承修复且报告未捕获。

- 教训：上版遗留问题清单是下版改动设计的强制输入（闭环流程第 2 步已固化）

### 坑 5：prepare 脚本清空重建目录，多版产物互踩

prepare_split_input.py 会清空重建 module 目录，v1 产物在 v2 启动后被清掉。

- 教训：多版对比必须串行执行 + 每版跑完立即快照隔离（闭环流程第 3 步已固化，三版对比第 8 节）

### 坑 6：journal 回放是廉价的失败恢复

v2 首跑失败用 resumeFromRunId 续跑，Phase 1 的 13 个 agent 从 journal 零成本回放。

- 教训：执行失败先 resume 再谈重跑；失败原因本身是评审证据（三版对比第 8 节）

## 三、评审维度模板

机制类（可归因，必须程序化复算）：

- 编号落地率：数据行编号连续唯一数 / 数据行总数；AUTO 残留数
- 闸门闭环：机械结论与报告结论双向一致；REVIEW_RESULT 与四维明细行数对账
- 元信息回填：占位符残留数；被校验文件列全率
- 锚点纪律：引用的源锚点悬空数（程序化核验）
- 表格结构：表头列数与数据行列数一致率

内容类（有随机波动，只评不归因）：

- 覆盖完整性：关键判定条件非空、术语别名项数、操作行覆盖面
- 结构规范性：配置项要素齐全率、独立成行率
- 粒度与密度：拆分行数、REQ 密度、溯源覆盖

综合排名 = 各维奖牌汇总；元结论必须分"机制修复生效项"与"内容波动项"两栏陈述。

## 四、元指标口径

| 指标 | 来源 | 口径 |
|------|------|------|
| 耗时 | run 结果 | 秒，四版可比 |
| token | run 结果 | 全程总量（含评审前流程） |
| 轮次 | journal | 检查修复闭环走了几轮 |
| 流程结果 | run 返回 | passed / failed |
| 自评 | 产物报告 | RED/O/Y 计数，需与明细行数对账 |
| 评审耗时与 token | 评审 run | 单列，不与执行 run 混算 |
