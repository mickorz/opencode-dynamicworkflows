# workflow-optimize

## 能力概述

对 workflow DSL 脚本做一次完整的迭代优化：

备份旧版 → 一版一主题修改 → 真实执行 → 产物快照隔离 → 多并行评审 agent 多维对比 → 写演进报告 → 新经验回填踩坑库。

每次迭代都留下三样东西：可追溯的版本备份、可复算的质量对比报告、沉淀到 playbook 的新经验。

## 何时使用

- 用户说"优化 workflow / 迭代脚本 / 改一版"
- 用户要评估"这次改动有没有效果"、"对比 vN 和 vN+1"
- 用户要复盘 workflow 执行失败或产物质量问题
- 用户提到"备份旧版"、"参悟上版经验"、"多维评审"

## 能力边界

- 负责：workflow DSL 脚本本身的优化迭代与效果评审方法论
- 不负责：workflow 引擎 / OpenCode 插件功能开发（src/ 的活）；非 workflow 的普通业务代码优化
- 不负责：跳过执行直接评审——效果结论必须来自真实执行产物，不接受纯静态推断

## 输入

| 输入 | 必需 | 说明 |
|------|------|------|
| 目标 workflow 脚本 | 是 | 当前工作版路径 |
| 优化目标或问题报告 | 是 | 本版要修什么（上版报告的遗留问题清单优先作为输入） |
| 评审基准 | 否 | 无则用历史版本产物目录（quality-compare/） |

## 输出

1. 持续维护的优化档案（每个被优化的 workflow 一套，schema 见 `reference/ledger-schema.md`）：
   - 优化台账：每版一行的流水索引
   - 指标对比：指标 x 版本矩阵（执行/机制/内容三组，口径固定）
   - 遗留问题清单：跨版记忆与状态流转
2. 备份文件：`<name>.v<N>-<标记>-<YYYYMMDD>.js`（放脚本同目录）
3. 新工作版：`<name>.js`（原地更新）
4. 产物快照：`<产物根>/quality-compare/v<N>/`
5. 演进报告：与历史对比报告同目录，含元数据、排名、根因、遗留问题
6. playbook 回填：新踩坑与新验证有效的修复手法记入 `reference/optimize-playbook.md`

## 路由

| 场景 | 进入 |
|------|------|
| 执行一次完整迭代闭环 | `process/optimize-iteration-flow.md` |
| 设计改动前查已验证修复手法与踩坑 | `reference/optimize-playbook.md` |
| 初始化优化档案、查指标口径与写入时机 | `reference/ledger-schema.md` |

三个文件都要用：先查 playbook 设计改动，档案结构按 ledger-schema 建立与维护，再按 flow 执行闭环。

## 核心原则（能力级，违反即评审无效）

1. 一版一主题：多主题混改导致无法归因，宁可拆成两版
2. 效果结论只认真实执行产物 + 程序化复算，不认报告自述
3. 机制维度与内容维度分开评审：内容有随机波动，机制修复才能归因
4. 上版报告的遗留问题清单必须传递到下版设计（跨版记忆）
5. 执行产物必须立即快照隔离，防止下版执行清空重建目录时丢失

## 路径推导规则

不假设固定目录，一切从目标脚本自身推导：

- 运行目录：脚本内相对路径（如 `.xflow/...`、`.opencode/skills/...`）的解析基准 cwd，从脚本内容读出；推导不出时询问用户在哪个目录执行，禁止假设为当前目录
- 脚本备份：目标脚本所在目录
- 产物快照：`<运行目录下 workflow 的产物输出根>/quality-compare/v<N>/`（产物输出根同样从脚本内容推导）
- 演进报告：项目文档目录；已有历史演进报告则与其同目录，没有则放项目文档目录（如 Docs、docs）
