# LLM Workflow Generation A/B 执行报告（P1-5 实测）

> 实验日期：2026-09-24 · 单轮全量（20 prompt x 2 组）· 生成模型 deepseek-v4.1-flash-official（headless，逐条独立会话）
> 方案：`LLM-Generation-AB评估方案.md` · 驱动器：`examples/sample-project/ab-driver.mjs`（状态 `ab-state.jsonl`，原始会话日志 `ab-logs/`）

## 结论（判定门槛裁决）

**Composite API 未显示明显提升（首过生成率 -5pp，未达 ≥10pp 提升门槛）→ 按方案判据：维持现状，冻结 DSL 扩展**（P2-4 装饰节点不做的决策获得实测佐证）。

关键洞察：**两组的失败都集中在「会话执行行为」而非 API 表达力**——探索过头、要求澄清原文、超时未落盘；一旦脚本落盘，两组首过执行成功率都是 100%（skill 的语法自检步骤均有效）。

## 分类别首过生成（n=4/类，仅参考——小样本噪声大）

## 生成失败原因分类（会话日志溯源）

| 类型 | A 组 | B 组 |
|---|---|---|
| 模型反问澄清（要求"需求原文"） | #9 | — |

修复轮把 A 的 #11/#19、B 的 #5/#9/#11 补生成并全部跑通——进一步证明是「执行行为」问题非能力问题。

## 可读性抽样（同题对照 #9 快慢模型降级）

- A（a-09）：手写候选循环 + 状态位标，降级逻辑散在 if/throw 里
- B（b-09）：`fallback([...])` 三候选直陈，文件头注释自述「把降级语义交给运行时」，并主动设计了 `args.forceFail/forceQualityFail` 确定性演练面

主观评分：B 4/5 vs A 3/5——组合写法在**语义直陈与可演练性**上确实更优，但这属于质量收益，未转化为首过率。

## 局限与后续

1. 单模型单轮，n=20；类别内差异无统计效力
2. 生成失败归因于会话行为（timeout/澄清/探索），**换更强模型或加「直接写盘不要探索」指令可能让两组都到 95%+**——那是 prompt 工程问题，不是 API 问题
3. 若未来重测：建议 (a) 生成 prompt 禁止探索、要求直接落盘；(b) 加测修复轮（人为注入一个 bug 后比较修复质量）；(c) 强模型复测

## 对 V1.1 开发的直接影响

- P2-4 装饰节点（repeat/guard/invert/alwaysSuccess）：维持不做 ✅（实测支持）
- Composite 价值定位：**人类可读性与运行时观测（组合树/降级语义显式化）**，而非 LLM 生成正确率——与 P2-3 TUI 组合树的投入方向一致
