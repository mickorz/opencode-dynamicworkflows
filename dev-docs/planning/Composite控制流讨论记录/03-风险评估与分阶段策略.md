有必要先做风险评估。这次不是“加几个 helper”那么简单，因为一旦引入 `sequence / fallback / race`，再考虑弱化 `pipeline`，实际上是在改 **Dynamic Workflow 的控制流模型**。

结合你当前 Runtime 的真实约定，我认为开发前最需要守住的是：**旧 Workflow 行为不能因为新 Composite Node 被悄悄改变。**

你现在已有不少稳定契约：`agent()` 可恢复失败返回 `null`、不可恢复错误抛出；`parallel/pipeline` 的失败槽位是 `null`；`workflow()` 的参数和返回值通过 `structuredClone` 隔离；父子 workflow 共用并发、中断、journal；resume 又依赖调用位置和 `wfN` scope。([GitHub][1]) 这些都会被这次改造碰到。

## 我会把风险分成 8 类

| 风险                     |   严重度 | 最容易出问题的地方                    |
| ---------------------- | ----: | ---------------------------- |
| Success / Failure 语义变化 | 🔴 极高 | `null`、throw、`{ok:false}`    |
| Resume / Journal 失效    | 🔴 极高 | agent 调用位置、child `wfN`       |
| Pipeline 行为被错误替代       |  🔴 高 | item 并发、null 传播、stage 行为     |
| 并发与取消语义变化              |  🔴 高 | `parallel/race`、abort        |
| 子 Workflow 嵌套行为变化      |  🟠 高 | depth、cycle、structuredClone  |
| TUI / 统计树失真            | 🟠 中高 | Composite 层级、token/wall time |
| LLM 写法迁移风险             |  🟠 中 | skill/示例同时存在新旧写法             |
| API Breaking Change    |  🟠 中 | npm 现有用户的 `pipeline()`       |

其中前三项，我建议**设计没确定之前不要开写**。

# 1. 最大风险：千万不要用 `null / false` 简单定义 Node Failure

这是最先需要解决的问题。

你当前：

```js
const result = await agent(...)
```

可恢复失败：

```js
null
```

但 Workflow 业务结果可能是：

```js
{
    ok: false,
    errors: [...]
}
```

它在当前 Runtime 看来仍然是：

> workflow 正常执行完成。

当前文档甚至明确说明，子流程正常 return 就是 runtime `ok`，`{ok:false}` 这类业务结果不会改变执行状态。([GitHub][1])

所以绝对不能这么写：

```ts
if (!result) {
    return failure
}
```

否则：

```js
false
0
""
null
```

都有可能被误判。

尤其以后：

```js
fallback([
    () => workflow("validate.js"),
    () => workflow("repair.js")
])
```

如果：

```js
validate.js
```

返回：

```js
{ ok: false }
```

到底意味着：

```text
Workflow 执行成功
```

还是：

```text
Fallback 应该进入下一节点
```

这是两个不同概念。

### 我建议一定拆成：

```text
Execution Status

SUCCESS
FAILURE
CANCELLED
```

和：

```text
Business Result

任意 unknown
```

即：

```ts
interface NodeResult<T> {
    status: "success" | "failure" | "cancelled"
    value?: T
    error?: unknown
}
```

千万不要：

```text
value === null
=
failure
```

直接画等号。

这是整个改造最核心的设计点。

---

# 2. 但是第一版也不要直接修改 `agent()` 返回值

比如不要突然把：

```js
const result = await agent(...)
```

从：

```js
string | object | null
```

改成：

```js
{
    status,
    value
}
```

这会直接把现有脚本全部打坏。

当前公开 API 已经明确是 agent 成功返回文本/对象、可恢复失败返回 `null`。([GitHub][1])

所以内部可以变：

```text
AgentExecutionResult
        ↓
NodeResult
```

但外部继续：

```js
agent()
→ 原返回值
```

建议结构：

```text
                    Runtime Internal

                 executeAgentNode()
                       │
                       ▼
                   NodeResult
                       │
                  unwrapValue()
                       │
                       ▼
Public API          agent()
```

也就是说：

> **Node Protocol 是 Runtime 内部控制协议，不要强迫现有用户全部改写。**

---

# 3. `sequence()` 的 Failure 到底是什么，必须先写成规范

例如：

```js
await sequence([
    () => workflow("A.js"),
    () => workflow("B.js"),
    () => workflow("C.js")
])
```

至少要回答下面这些问题：

```text
A return null
→ 停吗？

A throw
→ sequence throw，还是返回 failure？

A return {ok:false}
→ 停吗？

A 被 abort
→ B 执行吗？

A timeout
→ B 执行吗？

A child workflow 配置错误
→ fallback 能不能吞掉？
```

这不能边开发边决定。

我建议规则是：

```text
Runtime success
    ↓
继续

Runtime recoverable failure
    ↓
sequence FAILURE

Runtime cancelled
    ↓
sequence CANCELLED

Runtime structural/config error
    ↓
THROW
```

特别是：

```text
unknown workflow
cycle detected
max depth exceeded
invalid schema
invalid node definition
```

这些不要让：

```js
fallback(...)
```

悄悄吞掉。

因为它们不是：

> “A 方案没成功。”

而是：

> “Workflow 写错了。”

# 4. Resume / Journal 是这次最大的回归区域

当前 resume 有非常强的约束：

```text
agent/checkpoint
按照调用位置匹配
```

修改前面的调用以后，后面的缓存就会失效。([GitHub][1])

子 Workflow 又是：

```text
runId:wfK:N
runId:wfK:wfM:N
```

其中 `wfK` 本身也是按调用顺序编号。重排 child workflow 会导致后面的 child scope 重排并重跑。([GitHub][1])

现在加入：

```js
sequence([
    A,
    B,
    C
])
```

首先要坚持一个原则：

> **Composite Node 本身第一版不要消耗 journal callIndex。**

否则旧：

```js
await agent("A")
await agent("B")
```

可能是：

```text
0 A
1 B
```

新：

```js
sequence([
    () => agent("A"),
    () => agent("B")
])
```

如果 sequence 自己占一个 journal index：

```text
0 Sequence
1 A
2 B
```

Resume 兼容性马上没了。

第一版应该：

```text
sequence
  ↓
只控制执行

agent/workflow/checkpoint
  ↓
仍然按照原规则 journal
```

也就是：

```text
Composite = transparent to journal addressing
```

这个非常重要。

---

# 5. 更麻烦的是 fallback / race 会改变“哪些调用发生”

例如：

```js
fallback([
    A,
    B,
    C
])
```

第一次：

```text
A failure
B success

C 不执行
```

resume 后如果 A 因某些输入变化成功：

```text
A success

B/C 不执行
```

那么之后的 call index 会发生漂移。

这会影响：

```text
后续 Agent journal
child workflow wfN
checkpoint
```

所以你需要提前定义：

> **控制流发生变化以后，Resume 允许从该分支点以后全部失效并重跑。**

不要试图第一版解决：

```text
branch-aware resume
stable node id
content-addressed composite journal
```

那会让改造范围瞬间翻倍。

第一版接受：

```text
分支变化
     ↓
该点之后 cache miss
     ↓
重新执行
```

是完全可以接受的。

但是必须测试并写到文档。

---

# 6. Pipeline 暂时绝对不要删除

这是我现在最想强调的一点。

我们前面说：

```js
pipeline(items, A, B, C)
```

看起来可以变成：

```js
parallel(
    items.map(item => () =>
        sequence([
            () => A(item),
            prev => B(prev),
            prev => C(prev)
        ])
    )
)
```

概念上没问题。

但是**执行语义未必完全等价**。

当前 pipeline 明确定义：

> 每个 item 依次流过所有 stage，不同 item 之间并发，而且没有 stage barrier。([GitHub][1])

这里有至少四个风险。

### 风险 A：null 是否继续传

现在可能是：

```text
A(item) → null
             ↓
          B(null)
             ↓
             C
```

但如果 sequence 定义：

```text
null → FAILURE → STOP
```

语义就变了。

---

### 风险 B：调度公平性

Pipeline 可能是：

```text
item1 A → B → C
item2 A → B → C
item3 A → B → C
```

共享全局 semaphore。

而：

```js
parallel(items.map(() => sequence(...)))
```

虽然结果可能一样，

但：

```text
哪个 stage 先获得 agent slot
```

可能不同。

这会影响：

```text
wall time
token spending timing
abort timing
journal call order
```

---

### 风险 C：纯 JS stage

你现在 Pipeline stage 不要求是 Agent：

```js
async (summary, file, i) => ({
    file,
    index: i,
    summary
})
```

当前文档已经支持这种纯 JS 数据整形。([GitHub][1])

新 sequence 必须也支持普通 async/sync callback，否则 pipeline 无法等价迁移。

---

### 风险 D：大数组内存

比如：

```text
1000 items
```

如果：

```js
parallel(
    1000 × sequence(...)
)
```

一次创建 1000 个 Promise chain，

而旧 pipeline 如果内部有自己的调度方式，内存/队列行为可能不同。

所以我的建议变成：

> **先保留 pipeline 原实现。**

等 Composite 完成以后做：

```text
Pipeline Old
vs
Parallel + Sequence
```

A/B。

确认：

```text
结果一致
失败行为一致
执行顺序可接受
resume 行为一致
并发峰值一致
内存没有恶化
```

再决定：

```text
pipeline → helper
```

而不是现在直接删。

---

# 7. `race()` 的 Abort 是非常高风险区域

比如：

```js
race([
    () => workflow("A.js"),
    () => workflow("B.js"),
    () => workflow("C.js")
])
```

B 先成功。

理想：

```text
A ── abort
B ── success
C ── abort
```

问题是你当前：

> 父子 workflow 共享 abort signal，且子 workflow 又可能包含多个 agent。([GitHub][1])

所以 race 不能直接：

```js
controller.abort()
```

否则可能把整个 Root Workflow 都停掉。

需要：

```text
Root AbortController
        │
        ├── Composite local controller
        │       ├── A
        │       ├── B
        │       └── C
        │
        └── 后续节点
```

即：

```text
Race winner
     ↓
abort sibling scope

NOT

abort root run
```

这需要明确的：

```text
Abort tree
```

否则 race 很容易成为最危险的新节点。

所以我甚至建议：

```text
sequence
fallback
```

先做。

`race` 第二阶段。

---

# 8. Parallel 也不要顺手重写

你现在 `parallel()` 已经稳定承担：

```text
并发限制
input order
null slot
agent queue
```

([GitHub][1])

这次可以让它：

```text
进入 Composite 模型
```

但第一版最好：

> **包装现有 parallel，而不是重写 parallel。**

例如：

```ts
Composite.parallel()
      ↓
existingParallel()
```

不要趁机：

```text
sequence
fallback
race
parallel
pipeline
```

五个一起重构。

这类“大一统重构”最容易出现：

> 功能都能跑，但一些 resume / TUI / timeout 边角全坏了。

---

# 9. 子 Workflow 的 `structuredClone` 要保留

现在：

```js
workflow("child.js", args)
```

args 和返回值通过 `structuredClone` 隔离。([GitHub][1])

那么：

```js
sequence([
    () => workflow("A.js"),

    prev => workflow(
        "B.js",
        { prev }
    )
])
```

不要因为 sequence 内部传 `prev` 就绕过现有 `workflow()` 边界。

应该还是：

```text
A result
   ↓
sequence prev
   ↓
workflow(B,args)
   ↓
structuredClone
   ↓
B
```

而不是：

```text
Sequence 自动共享 object reference
```

否则 child A 修改：

```js
obj.foo = ...
```

可能意外影响父/其他 child。

这会破坏现在非常好的隔离特性。

---

# 10. TUI 第一版不要做得太深

你现在 TUI 已经展示：

```text
Workflow
  └ Child Workflow
        └ Phase
              └ Agent
```

而 journal 又有：

```text
workflowPath
workflowScopePath
workflowLabel
```

([GitHub][1])

以后我们当然想展示：

```text
▼ Sequence
   ✓ A

   ▼ Parallel
      ✓ B
      ✓ C

   ▼ Fallback
      ✗ D
      ✓ E
```

但我建议：

### Runtime 第一版

先：

```text
Composite 执行正确
```

### TUI 第二步

再：

```text
Composite visibility
```

不要反过来为了显示树，马上修改：

```text
journal schema
run-store
agent record schema
TUI tree builder
```

这样改造面积会一下扩大很多。

第一版哪怕 TUI：

```text
A
B
C
D
```

仍保持旧显示，都比：

> Runtime + TUI + Journal 同时大改

安全。

# 11. 给 Composite Node 一个“纯控制层”边界

这个架构边界建议开发前写在设计文档第一页：

```text
Composite Node DOES:

✓ 决定执行顺序
✓ 决定是否继续
✓ 组合已有 Node
✓ 传播 cancellation
✓ 返回组合结果

Composite Node DOES NOT:

✗ 创建 Agent
✗ 管理模型
✗ 自己记 token
✗ 自己生成 journal agent entry
✗ 自己管理 worktree
✗ 改 structuredClone 规则
✗ 自己实现 concurrency semaphore
```

也就是说：

```text
Composite
    │
    ▼
调用现有 Runtime primitives
```

而不是：

```text
Composite
    ↓
重新实现 Runtime
```

这个边界会帮你避免很多坑。

---

# 12. `sequence(prev)` 的数据模型第一版保持简单

我现在更建议第一版甚至不要直接上：

```js
(prev, ctx)
```

各种复杂上下文。

先：

```js
sequence([
    () => A(),
    prev => B(prev),
    prev => C(prev),
])
```

返回：

```text
最后一个 Node 的 value
```

够了。

如果用户需要多个历史值：

普通 JS：

```js
let analyze

await sequence([
    async () => {
        analyze = await workflow("analyze.js")
        return analyze
    },

    design => workflow("develop.js", {
        analyze,
        design
    })
])
```

或者第二版再加：

```js
(prev, ctx)
ctx.results
```

原因是：

> **第一次改造越少引入隐式状态越好。**

你现在最重要的是验证：

```text
Composite Model 是否成立
```

不是一次把 API 做满。

# 13. LLM Skill 必须跟 Runtime 分开发

这是你的项目和普通库不一样的地方。

README 当前的产品路径是：

```text
用户自然语言
→ Main Agent
→ workflow-authoring skill
→ 生成 JS Workflow
```

([GitHub][2])

所以 Runtime 做完以后不能直接把 Skill 改成：

```text
以后全部必须 sequence
```

建议有一段灰度期：

```text
简单串行：

const a = await workflow(...)
const b = await workflow(...)

仍然推荐普通 JS。


真正的组合控制：

fallback
parallel
sequence nesting

才使用 Composite。
```

否则 Main Agent 可能把所有：

```js
await A()
await B()
```

都机械变成：

```js
sequence([A, B])
```

反而让脚本更啰嗦。

# 最后我给这次改造划一条红线

这次 V1 **只做控制流抽象**：

```text
              Composite Layer
                    │
        ┌───────────┼───────────┐
     sequence     fallback    existing parallel
        │             │             │
        └─────────────┼─────────────┘
                      ↓
               Existing Runtime
                      ↓
      agent / workflow / journal / resume
```

暂时不要同时做：

```text
× .flow DSL
× stable node ID
× journal 新格式
× pipeline 删除
× TUI 全量树重构
× runtime public return type 大改
× parallel 重写
× while/repeat/random
```

如果把这些一起做，这就不叫新增功能了，而是在**换 Workflow Engine 内核**。

你现在已经有 91 个 commits，原生子 workflow、journal/resume、并发、TUI、schedule 等不少功能都建立在现有运行语义上。([GitHub][2]) 所以这次最合理的原则是：

> **Add Composite Layer, don't rewrite the Engine.**

尤其我现在会把两个东西定为开发前必须先完成的设计文档：**① Node Success/Failure Contract；② Journal/Resume Compatibility Contract。** 这两个没定下来，我不建议直接开始写 `sequence()`，因为后面最容易推倒重来。
