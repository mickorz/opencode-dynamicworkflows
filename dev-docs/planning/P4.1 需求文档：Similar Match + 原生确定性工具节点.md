# P4.1 需求文档：Similar Match + 原生确定性工具节点

> P4 已封版（`36efab8` 主体 + `d1237d8` 收尾，均已在 main）：跨 Run Exact 聚合 -> 候选生成
> （replace-with-tool）-> 双 worktree A/B -> 人工审批 -> 多文件事务应用，全链实机验收通过。

>  1. **Similar Match**：突破 Exact Match 的同路径同内容限制，识别跨 Run 的逻辑相似脚本
>  2. **原生确定性工具节点**：提供比 `check()` 更强的零 token 业务逻辑承载原语，
>     并在本期放开纯确定性 Workflow（零 Agent）
>
> 本文档是需求文档（What 与 Why），不做详细设计（How 留给执行文档）。
> 基线：main `270a695`，测试 563 通过。
>
> v1.1（评审修订）：外部评审 4 个 P0 全部核实成立并采纳——
>  1. runTool 失败语义改为默认抛错（node-contract 的 resolve 即 success 语义下，返回 {ok:false} 不会触发 fallback）

>  3. Similar Match 匹配结果三分类（exact / similar-candidate / reviewed-compatible），常量不折叠
>  4. 纯 Tool Workflow 从 P4.2 提前到本期（agentCount === 0 && toolCount === 0 才拒绝）

## 一、背景与动机

### 1.1 Exact Match 的漏检现实

P4 的 `candidateFingerprint = sha256(category + sourceTool + filePath + contentHash)` 是严格
Exact Match：同一脚本在**同一路径**且**内容完全相同**时才聚合。真实使用中，Agent 每次重写
"同一逻辑"的临时脚本时，天然存在以下差异：

| 差异来源 | 例子 | Exact 结果 |
|---------|------|-----------|
| 路径不同 | `temp/validate.py` 与 `tmp/check_config.py` | 不聚合 |
| 变量名不同 | `config` 与 `cfg` | 不聚合 |
| 注释与空行 | 顺手多写一行注释 | 不聚合 |
| 参数化程度 | 一次硬编码路径、一次用 `sys.argv` | 不聚合 |
| 小幅演进 | 加了一个边界判断 | 不聚合 |

后果：`distinctRunCount` 增长缓慢，大量真实的固化机会停留在 `runs=1` 永远达不到聚合门槛
（>=2），P3 的 Optimizer 审阅也反复对"几乎相同"的候选各写一份报告。

P4 实机数据佐证：`fp=4b3fa726` 能聚合是因为验收样本刻意让 Agent 每次写完全相同的
`p3_validate.py`（prompt 中给出全文）。真实场景下 Agent 输出逐字复现并不可靠。

### 1.2 `check()` 承载力的天花板

P4-B 的 `replace-with-tool` 把"写脚本 Agent"替换为：

```javascript
await check(() => commandSuccess("python tools/p3_validate.py opencode.json"), "固化工具可用性检查")
```

它解决了 token 浪费，但表达能力止步于布尔：

- **拿不到输出数据**：固化脚本 stdout 里的业务结果（如校验明细、统计数字）被丢弃，
  后续节点若需要，仍得派 Agent 重新执行并转述（token 又回来了）
- **失败无细节**：`commandSuccess` 只有 true/false，失败原因（脚本异常、参数错、数据非法）
  不可分辨，`fallback()` 无法按失败原因选分支
- **执行节点仍是 Agent**：P4 只固化了"写脚本"节点；"执行脚本并报告输出"的 Agent
  （每次花 token 读 stdout 转述）没有被固化，因为 `check` 表达不了"转述输出"
- **临时约束仍在**：候选必须保留至少一个 Agent/Checkpoint（P4 执行文档 4.0.2 临时约束）。
  一个真正只需要"跑脚本拿结果"的 Workflow，仍被迫保留无意义的 Agent

### 1.3 第三轮评审的定位

评审原文（P4 v2 评审修订 v3）：P4 第一版允许保留确实需要推理的 Agent，但不应靠添加无意义
Agent 来满足 Runtime 限制；后续应增加能够调用确定性脚本并返回结构化输出的原生节点。

P4.1 就是兑现这两条：Similar Match 扩大"值得固化"的识别面；原生工具节点提升"固化后"
的表达上限。

## 二、需求一：Similar Match

### 2.1 目标

跨 Run 识别"业务逻辑相似"的脚本化动作，合并为同一聚合候选；识别必须是分级的、可追溯的、
误报可拦的。

### 2.2 四级匹配模型与三类匹配结果

| 级别 | 名称 | 机制 | 成本 | 误报率 | 用途 |
|------|------|------|------|--------|------|
| L0 | Exact | 现行 fingerprint（sha256 of path+content） | 零 | 零 | 保持不变，P4 行为兼容 |
| L1 | 规范化匹配 | 剥注释/空白/引号风格规范化后哈希 | 零（纯代码） | 低 | 聚合同脚本微改写 |
| L2 | 结构指纹 | 词法 token 化 + 标识符替换占位（常量不折叠）的形状哈希 | 零（纯代码，不引入解析器依赖） | 中 | 聚合重命名与参数化变体 |
| L3 | LLM 复核 | 对 L1/L2 候选对做业务等价评审 | 一次 Agent 调用每对 | 低（人工审批兜底） | 降误报，产出评审意见 |

**常量不折叠（v1.1 采纳）**：L2 结构指纹仅替换标识符名，**保留**字符串字段名、比较阈值、
协议名称、配置键名等常量。校验 age >= 18 与校验 age >= 65 结构相同但阈值不同，不得同组。
误报优先于漏检。

**匹配结果三分类（v1.1 采纳）**：

| 结果 | 意义 | 是否允许自动生成 |
|------|------|----------------|
| exact | 源码精确匹配（L0） | 沿用 P4 自动链 |
| similar-candidate | 仅结构相似（L1/L2 达标，未经复核） | **不允许**，停在待人工确认 |
| reviewed-compatible | 经 L3 复核且人工确认，认为值得共同固化 | 可进入生成，仍需 A/B 与审批 |

设计约束：

- **L1/L2 是确定性代码**（宿主无关，进 aggregator），不引入 AST 解析依赖（项目零新依赖原则；
  Python 侧无现成解析器，自研词法折叠以够用为限，明确标注为启发式）
- **L3 只做复核不做发现**：候选对必须先由 L1/L2 产生；复核结论是**评审意见，不能证明行为
  等价**（因此 reviewed-compatible 仍需 A/B 实证）
- 每条 occurrence 保留：原 L0 指纹 + 规范化指纹 + 结构指纹 + 所属相似组 ID，全程可追溯回
  原始证据（evidenceRefs 不变）

### 2.2.1 相似组形成规则（组 ID 稳定性与非传递性）

相似关系不传递（A 近似 B、B 近似 C、A 不近似 C），组形成采用**锚点代表制**：

- 组 ID 由**组内最早出现脚本的规范化指纹**派生（不随后续成员变化而变，跨轮次稳定）
- 新脚本只与**当前各组锚点**比对，命中则入组；**不做链式合并**（组成员间不互相扩大组）
- L1 与 L2 分别成组不混组；锚点与成员的匹配级别记入组元数据

### 2.3 聚合模型扩展

candidates.json 演进（保持 schemaVersion 兼容读取）：

- matchMode: exact | similar（组级标记，对应三分类的 exact 与 similar-candidate / reviewed-compatible）
- 相似组新增 similarityGroupId（**锚点代表制**派生，见 2.2.1）、
  matchResult: similar-candidate | reviewed-compatible、matchLevel: L1 | L2 | L3
- distinctRunCount 门槛、patchEligible 判定、按目标 Workflow 分离逻辑全部沿用 P4 语义
- bestConfidence 语义对齐三分类：similar-candidate 上限 low；reviewed-compatible 上限
  medium（L3 是评审意见非行为证明）；high 仍保留给 exact + 双证据链

### 2.4 误报防线（核心需求，不可裁剪）

结构相似但业务不同的脚本（例如两个都是"读 JSON 校验字段"但校验的是不同配置）是主要误报源。
防线按层次：

1. **相似组不自动进入候选生成**：similar 组（L1/L2 达标）默认停在"已聚合待确认"，
   需要一个人工确认动作（复用 optimization_control：新增 `confirm` action 或等价交互）
   才允许 P4-B 生成候选。Exact 组维持 P4 自动链不变
2. **生成时按组内代表脚本固化**：representative 选择规则明确（最新 occurrence 优先，
   且要求其参数化程度组内最高），固化内容与该代表完全一致，不做跨脚本合成
3. **A/B 功能等价闸门沿用**：deterministicCheck 的 stdout 对比天然拦截"固化错了对象"
4. **人工审批闸门沿用**：approve 前一切可回退

### 2.5 边界（不做什么）

- 不做跨语言匹配（Python 变体只与 Python 变体比）
- 不做语义级 AST diff（明确是启发式，准确率靠 L3 与人工兜底）
- 不自动合并不同 `suggestedTarget` 路径的部署目标（组内各 occurrence 的目标路径可不同，
  固化产物部署路径取代表脚本的；其余路径的清理建议只写进报告，不动文件）

## 三、需求二：原生确定性工具节点

### 3.1 目标

提供 DSL 原语：以零 token 调用项目内确定性脚本，返回**结构化输出**，可参与组合控制流，
作为被固化业务逻辑的标准承载。

### 3.2 DSL 形态（候选签名，最终以执行文档为准）

```javascript
const result = await runTool("tools/validate.py", {
  args: ["opencode.json"],       // 位置参数（字符串数组，不经 shell 拼接）
  timeoutMs: 30_000,             // 与 commandSuccess 同缺省
  parseJson: true,               // stdout 为 JSON 时自动解析
  onFailure: "throw",            // 缺省 throw；显式 "return" 才返回失败对象
})
```

**失败语义（v1.1 采纳，双模式，默认抛错）**：

- 缺省 `onFailure: "throw"`：非零退出码/超时/启动失败抛 **TOOL_FAILED**（可恢复错误，
  与 CHECK_FAILED 同构）——组合控制流直接感知：sequence 停止、fallback 换候选、
  parallel 塌缩 null、重试生效
- 显式 `onFailure: "return"`：正常返回结果对象（业务自行检查 ok/exitCode/stderr），
  用于需要获取错误详情做分支的场景
- 理由（源码核实）：node-contract.ts 的 executeNode 判定是"Promise resolve 任意值（含
  {ok:false}）即 success"，runTool 若缺省返回失败对象，fallback 不会切换候选

成功路径（onFailure 两种模式一致）返回：

```javascript
// {
//   ok: boolean,                 // exitCode === 0
//   exitCode: number,
//   stdout: string,
//   stderr: string,
//   durationMs: number,
//   parsed?: unknown,            // parseJson 且 stdout 可解析时存在
// }
```

**Journal 与 Resume（v1.1 采纳：记执行记录，不回放结果）**：

- **执行记录**：每次 runTool 执行写 journal entry（hash 覆盖 脚本路径 + 参数 + 工具文件
  内容哈希 + stdout 哈希 + 状态），供 Trace/TUI/审计；同时参与 run 的调用序身份
- **结果不回放**：Resume 时 runTool 一律**重跑**（执行成本低且确定性）
- **下游依赖失效**：下游 Agent 若在 prompt 中嵌入 runTool 输出（如上例 data.parsed），
  重跑后输出变化 -> prompt 变 -> journal hash 变 -> 该 Agent 自动重跑。该机制由既有
  "hash 覆盖 prompt/model/phase/agentType/schema"保证，P4.1-B 必须以专项测试锁定
  （防回归：runTool 输出变化时，下游 Agent 不得复用旧缓存）
- **dispatch 计数**：runTool 计入 toolCount、不计入 agentCount；有效性约束见 3.5

**工具执行边界（v1.1 采纳，非沙箱内的最小防线）**：

- 路径：仅允许项目目录内（相对 cwd 解析）的脚本；拒绝符号链接指向项目外
- 扩展名白名单（第一版）：.py / .js / .sh（Windows 下 .sh 不假定可执行，启动失败即失败）
- 参数经数组传递不经 shell 拼接（与 commandSuccess 的 exec 差异：无注入面）
- 输出大小上限（stdout/stderr 截断，超限视为失败）
- **确定性声明**：runTool 是"确定性调度节点"，不证明脚本本身确定（脚本仍可能访问网络/
  时间/文件）；固化候选的确定性由 P3 的 determinism 评估沿用，A/B stdout 对比兜底

### 3.3 Runtime / TUI / 周边适配面

| 适配点 | 需求 |
|--------|------|
| `workflow-runtime.ts` | 注入 `runTool` 全局；超时/abort 语义与 agent 一致（run 级中断可取消） |
| `workflow.ts` 工具描述 | 脚本规则说明加入 runTool |
| TUI | 新节点类型（确定性工具节点，区别于 agent 节点）：显示脚本路径、退出码、耗时；不显示 token |
| `workflow-authoring` skill | 新原语文档与示例 |
| resume / journal | 重跑语义（见 3.2），回归测试覆盖 |
| `check` 兼容 | `check(commandSuccess(...))` 模式保留（P4 已产出的候选仍合法） |

### 3.4 与 P4 闭环的衔接（候选生成升级）

P4-B 的替换策略库扩展：

| 策略 | 替换对象 | P4 状态 | P4.1 变化 |
|------|---------|---------|-----------|
| replace-with-check | 写脚本 Agent -> `check(commandSuccess)` | 已实现 | 保留 |
| **replace-with-tool**（新） | 执行脚本 Agent -> `runTool` + 后续节点消费 `parsed` | 无 | 新增：执行节点 Agent 也被固化，收益上限大幅提高 |
| narrow-scope | prompt 收窄 | 已实现（执行节点路径替换） | 保留 |

候选校验同步扩展：替换后必须满足"剩余 dispatch >= 1"或"脚本含至少一个 Agent/Checkpoint"
（约束未变，只是替换选项变多）。

A/B 验证沿用：`deterministicCheck` 对比物不变；执行节点替换后的功能等价由
runTool 的 stdout 与原 Agent 转述输出中的关键标记比对（判定规则写入执行文档）。

### 3.5 临时约束的退出（v1.1：提前到本期完成）

P4 执行文档 4.0.2 的"至少一个 Agent/Checkpoint"临时约束在 **P4.1 放开**：

- Runtime 有效性判定从 `agentCount === 0` 扩展为 `agentCount === 0 && toolCount === 0`——
  纯 runTool Workflow（零 Agent、零 token）合法
- 放开理由（评审采纳）：runTool 的 Runtime/Journal/Abort/TUI/组合控制流适配本来就是
  P4.1-B 的核心工作，纯 Tool 场景与它共享同一组运行时基础，单独立版反而两次动同一处内核
- 配套必须补齐（不满足则不开）：纯 Tool Run 的 Journal 身份、Abort 级联、Trace 采集、
  TUI 展示、Resume 重跑、阶段闸门语义的专项测试；并回填 P4 执行文档 4.0.2 的
  架构决策变更记录（该文档已预留此钩子）
- P4-B 候选生成同步升级：双 Agent 场景（写脚本 Agent + 执行转述 Agent）可全部固化，
  产出零 Agent 候选；A/B 与审批链路不变

## 五、验收标准

| 编号 | 验收项 | 验证方式 |
|------|--------|---------|
| V41-1 | L1：仅注释/空白/引号差异的脚本聚合为同组 | 单元测试（fixture 对） |
| V41-2 | L2：变量重命名/参数化变体聚合为同组 | 单元测试 |
| V41-3 | 阈值/字段名/配置键不同的脚本**不**同组（常量不折叠） | 单元测试（反例 fixture） |
| V41-4 | similar-candidate 不自动生成；reviewed-compatible 才可进入且仍需 A/B | 单元测试 + 实机 |
| V41-5 | 相似组 ID 跨轮次稳定；非传递场景不做链式合并 | 单元测试 |
| V41-6 | runTool 缺省抛 TOOL_FAILED：fallback 换候选、sequence 停止、重试生效 | 单元测试 |
| V41-7 | onFailure return 模式：返回对象含 ok/exitCode/stderr/parsed | 单元测试 |

## 六、风险与对策

| 风险 | 影响 | 对策 |
|------|------|------|
| L2 结构指纹误报 | 固化错对象 | 人工确认门槛 + A/B stdout 对比 + 审批三道兜底；similar 组永不自动生成 |
| 词法折叠对非常规脚本失效 | 漏检（非误报） | 可接受：退化为 runs=1 不聚合，行为同 P4 |
| runTool 被滥用执行任意命令 | 安全 | 与 commandSuccess 同边界（项目内脚本）；文档明示非沙箱；不加宽 |
| 执行节点固化后 A/B 判定不稳（Agent 转述 vs 结构化输出） | 功能等价闸门误判 | 对比物仍取 deterministicCheck stdout（确定性），Agent 转述不进哈希（P4 既定原则） |
| candidates.json schema 变更破坏旧读端 | 兼容性 | 只加字段不改名不改义；matchMode 新值向后可忽略 |
| 范围蔓延（P4.2 事项混入） | 周期失控 | 3.5 明确退出条件不在本期；术语表与边界节逐条对照 |
