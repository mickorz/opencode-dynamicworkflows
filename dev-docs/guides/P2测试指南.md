## 测试一：后台运行 + 结果回传（F-18）

```
读取 scripts/background-test.js 的内容，用 workflow 工具执行并传 background: true
```

**通过标准**：
1. workflow tool **立即返回**（runId 一条提示，不是等 4 个 agent 跑完）
2. 紧接着随便问 Main Agent 一句别的（如"1+1 等于几"）——证明对话没被阻塞
3. 等后台跑完（约 20-40s），会话里**自动出现一条新消息**：`[后台工作流已完成...]` + 完整结果，Main Agent 接力汇报
4. 输出头部含 token 总数；若 provider 上报了成本，还会出现 `成本 $X.XXXX`（F-19）

## 测试二：workflow_control 控制（F-17）

**status**：

```
用 workflow_control 工具查询全部后台工作流状态
```
预期：列出 run（运行中在前，含 `X/N agent` 进度）。

**stop**（重跑测试一的后台脚本，趁运行中执行）：

```
用 workflow_control 工具停止 runId 为 <上一步返回的 runId> 的后台工作流
```

预期：
- 返回"已停止"提示
- 会话随后自动收到 `[后台工作流状态：aborted]` 消息，附 `resumeFromRunId="..."` 续跑提示
- 用 `resumeFromRunId` 续跑：已完成的分析直接缓存回放（结合 P1 测试二验证过的语义）

## 已知设计边界

- 后台 run 与 OpenCode 进程同生命周期：退出 OpenCode 则后台 run 终止（journal 保留已完成部分，重启后续跑）
- 后台 run 的 checkpoint 走 headless 默认值（无人工弹窗）
- pause 未单独实现：stop + resumeFromRunId 的 journal 回放语义天然等价（与 Pi 同思路）
